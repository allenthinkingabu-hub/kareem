# 6-Step Consulting Workflow — 详细展开 SOP

> 本文件是 `SKILL.md` Section 4 的完整参考展开版本。
> 适用于需要深入了解每步骤设计意图、边界条件和异常处理的场景。

---

## 总体设计原则

1. **透明优先**：每个关键决策节点必须向客户汇报，不做黑箱操作
2. **硬锁保障**：Step 2、Step 3 结束时设置不可绕过的客户确认拦截
3. **调研优先**：严禁在未完成 Step 4 调研的情况下进入 Step 5 生成答案
4. **满意度闭环**：客户不满意时无条件回到 Step 1，不设上限
5. **只读保护**：除 `consulting/` 子目录外，所有路径严禁写入

---

## Step 1: 📥 接收问题清单与任务定位 (Intake & Task Binding)

### 设计意图

防止 Consulting Agent 在错误的任务上下文中工作，确保问题定位精准。

### 详细执行流程

```
1.1 解析客户指令
    ├── 提取 Task ID（如 "Task 1.1" → task_id = "1.1"）
    ├── 提取问题编号（如 "Q3、Q5、Q7" → questions = [3, 5, 7]）
    └── 若指令模糊（如"帮我回答问卷"），询问：
        "请问您希望我回答哪个任务的问卷？请提供 Task ID（如 Task 1.1）"

1.2 定位工作区
    ├── 构建路径：2_agent_workspaces/[task-folder]/
    ├── 验证路径存在：若不存在，告知客户并终止
    └── 验证 phases/questionnaire.md 存在：若不存在，告知客户 Step 1-5 产物缺失

1.3 读取问题原文
    └── 从 questionnaire.md 中提取指定问题编号的原文

1.4 向客户复述确认
    ┌─────────────────────────────────────────────────
    │ 📋 问题清单确认
    │ Task ID: [TASK_ID]
    │ 工作区: 2_agent_workspaces/[task-folder]/
    │
    │ Q3: [问题原文]
    │ Q5: [问题原文]
    │ Q7: [问题原文]
    │
    │ 请确认：以上问题清单正确？(确认/修改)
    └─────────────────────────────────────────────────

1.5 初始化状态机
    └── 创建 consulting/.consulting_state.md（见模版）
```

### 异常处理

| 异常情况 | 处理方式 |
|---|---|
| Task ID 不存在 | 告知客户，列出可用的 task-folder 列表 |
| questionnaire.md 不存在 | 告知客户主 Agent 尚未完成 Step 5，无法咨询 |
| 问题编号超出范围 | 告知客户，询问是否重新指定 |

### 拦截点

客户回复"确认，继续"后，更新状态机 `Step 1: DONE`，进入 Step 2。

## Step 2: 🔍 检索被咨询任务的关联资料 (Context Retrieval & Source Declaration)

### 设计意图

让 Consulting Agent 在调研前充分理解已有上下文，避免重复劳动和资料遗漏。同时通过透明汇报建立客户信任。

### 详细执行流程

```
2.1 读取全部 Step 1-5 产物
    ├── config/required_skills.yaml
    ├── config/required_tools.yaml
    ├── phases/phase4_research_conclusion.md
    ├── phases/phase4_research_trace.md
    ├── phases/questionnaire.md
    └── phases/ 下的其他产物（phase1_*.md, phase2_*.md 等）

2.2 逐题匹配相关段落
    对每个问题 Q[N]：
    ├── 在 phase4_research_conclusion.md 中检索相关段落
    ├── 在 required_skills.yaml 中检索匹配的专家角色
    ├── 在上游 OUT 文档中检索相关决策背景
    └── 记录每条资料的来源文件和段落位置

2.3 向客户透明汇报资料引用计划
    ┌─────────────────────────────────────────────────
    │ 📋 资料检索报告
    │
    │ Q3 将引用：
    │   - phase4_research_conclusion.md § 第3节
    │   - OUT-0.2.md § 技术约束部分
    │
    │ Q5 将引用：
    │   - required_skills.yaml 中的专家角色定义
    │   - phase4_research_conclusion.md § 第5节
    │
    │ Q7 将引用：
    │   - phase4_research_trace.md § 信息源清单
    │
    │ 请确认资料范围，我将基于以上资料进行调研 (确认/调整)
    └─────────────────────────────────────────────────
```

### 🛑 物理硬锁

**必须等待客户明确回复"确认资料范围，继续"后方可进入 Step 3。**

任何形式的自动推进均属严重违规。即使客户长时间未回复，也必须等待，不可超时自动跳过。

### 拦截点

客户确认后，更新状态机 `Step 2: DONE`，进入 Step 3。

## Step 3: ⚙️ 自身能力装配 (Self Capability Assembly)

### 设计意图

让 Consulting Agent 在调研前明确自己的专家身份和工具配置，确保调研方向精准，质量可控。

### 详细执行流程

```
3.1 推导专家角色
    根据问题域判断所需专家角色：
    ├── 技术类问题 → 系统架构师 / 云计算专家 / 安全工程师
    ├── 业务类问题 → 产品经理 / 业务分析师 / 行业顾问
    ├── 合规类问题 → 法务顾问 / 合规专家 / 数据隐私顾问
    └── 成本类问题 → 财务分析师 / FinOps 专家

    生成 consulting/consulting_skills.yaml

3.2 推导工具需求
    ├── 确认需要的调研工具（web_search, document_reader 等）
    └── 明确禁用黑名单（内容农场抓取等）

    生成 consulting/consulting_tools.yaml

3.3 规划调研清单
    对每个问题规划：
    ├── 具体调研关键词
    ├── 目标信息源类型（RFC/白皮书/技术博客）
    └── 预期找到的信息类型

    生成 consulting/consulting_research_plan.md

3.4 向客户汇报
    ┌─────────────────────────────────────────────────
    │ ⚙️ 能力装配报告
    │
    │ 主专家角色: [角色名]
    │ 辅助角色: [角色列表]
    │
    │ 启用工具: [工具列表]
    │ 禁用工具: [黑名单列表]
    │
    │ 调研计划:
    │   Q3: [调研方向和关键词]
    │   Q5: [调研方向和关键词]
    │   Q7: [调研方向和关键词]
    │
    │ 请同意调研计划后我将开始执行 (同意/调整)
    └─────────────────────────────────────────────────
```

### 🛑 物理硬锁

**必须等待客户明确回复"同意，开始调研"后方可进入 Step 4。**

### 拦截点

客户同意后，更新状态机 `Step 3: DONE`，进入 Step 4。

## Step 4: 📚 企业级深度调研 (Enterprise-Grade Research)

### 设计意图

确保所有答案都有坚实的企业级知识支撑，而非训练数据的泛泛而谈。

### 心智点火（强制）

```
🔥 [心智点火] Step 4 企业级调研开始
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
角色确认: [primary_role from consulting_skills.yaml]
技能确认: [domain_expertise 列表]
工具确认: [enabled 工具列表]
资料确认: Step 2 已加载 [N] 份文档，关键段落已摘录
目标确认: 待调研问题 Q[N1], Q[N2], Q[N3]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
所有确认通过，开始执行 Step 4 企业级调研
```

### 调研质量标准

| 标准 | 说明 |
|---|---|
| 企业级 | 大厂技术博客（Google、AWS、Netflix、Stripe 等）、RFC 标准、云厂商白皮书 |
| 专业性 | 来自领域权威机构或知名工程师（需有可验证身份） |
| 权威性 | 有明确出处（URL、文档名、版本号），可溯源 |
| 时效性 | 优先近 2 年内容，标注发布时间；2年以上内容需说明仍适用的理由 |

### 详细执行流程

```
4.1 按 consulting_research_plan.md 逐问题执行检索

4.2 对每个检索结果：
    ├── 验证来源质量（是否符合调研红线）
    ├── 提取核心信息点
    └── 记录完整溯源信息（URL/文档/发布日期）

4.3 生成 consulting/consulting_research_report.md
    结构：
    # 调研报告
    ## Q[N]: [问题]
    ### 调研思路
    ### 调研结论
    ### 应用方向（如何映射到本问题答案）

4.4 生成 consulting/consulting_research_trace.md
    对每条引用信息记录：
    - 来源名称
    - URL 或文档路径
    - 发布日期
    - 引用段落摘录
    - 质量评级（企业级/专业/权威/时效）

4.5 更新状态机 Step 4: DONE
```

## Step 5: ✍️ 生成答案 — 含强制心智点火 (Answer Generation with Mindset Ignition)

### 心智点火（强制，比 Step 4 更严格）

```
🚨 [强制心智点火] Step 5 答案生成开始
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
角色确认: [primary_role] + [supporting_roles]
技能确认: [完整技能列表]
工具确认: [已装配工具]
资料确认:
  - Step 2 上下文：[已加载文档数量] 份，[关键资料摘要]
  - Step 4 调研：[调研报告摘要] [溯源记录数] 条
目标确认: 逐题生成标准化建议答案 Q[N1], Q[N2], Q[N3]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
所有资料确认已加载，开始生成答案
```

### 答案生成规范

每题答案必须严格包含**完整 5 层结构**，参见 `assets/consulting_answer_template.md`。

**5 层结构要求**：
1. **问题解析**：非专业语言解释 + 指出对应模版配置项
2. **关键考量因素**：业务/技术/成本/合规 四维度，每维度至少 1 条具体内容
3. **解决思路**：至少 2 个方案（保守型/平衡型），含 Trade-off 分析
4. **企业级专业建议**：必须引用 Step 4 调研结论，含标杆企业案例
5. **Agent 可读回答**：格式化文本块，可直接粘贴给被咨询 AI Agent

### 质量检查（生成后自检）

```
对每题答案自检：
- [ ] 问题解析是否通俗易懂？
- [ ] 四维度是否均有覆盖？
- [ ] 方案是否有 Trade-off 分析？
- [ ] 专业建议是否引用了调研结论（含出处）？
- [ ] Agent 可读回答是否结构清晰可直接消费？
```

## Step 6: 📤 交付满意度闭环 (Delivery & Satisfaction Loop)

### 设计意图

通过逐题确认机制，确保每个答案真正满足客户需求，避免批量交付后返工。

### 满意度闭环流程

```
6.1 展示 Q[N] 建议答案（完整 5 层结构）

6.2 询问满意度
    ┌─────────────────────────────────────────────────
    │ 以上是 Q[N] 的建议答案。
    │ 请问您对此答案是否满意？
    │   ✅ 满意 → 请回复"满意"
    │   ❌ 不满意 → 请说明原因，我将重新为您调研
    └─────────────────────────────────────────────────

6.3a 若满意：
    ├── 标记该题状态 DONE
    ├── 更新 consulting_suggested_answers.md 中该题状态
    └── 继续下一题

6.3b 若不满意：
    ├── 记录客户反馈原因（详细）
    ├── 告知客户将携带反馈回到 Step 1 重新执行
    └── 回到 Step 1（不跳过任何步骤）
        注意：重新执行时将客户反馈作为额外约束条件

6.4 所有题目 DONE：
    ├── 更新 consulting_suggested_answers.md 状态为"客户已确认"
    ├── 生成最终标准化回答汇总（所有 Agent 可读回答的集合）
    └── 更新状态机 Step 6: DONE

6.5 最终宣告
    ┌─────────────────────────────────────────────────
    │ ✅ 咨询完成！
    │
    │ 所有问题建议答案已获客户确认。
    │ 产出文件位置: 2_agent_workspaces/[task]/consulting/
    │
    │ 您可以将 consulting_suggested_answers.md 中的
    │ "Agent 可读回答" 块直接提交给主 Agent 的 Step 6 访谈实录。
    └─────────────────────────────────────────────────
```

### 无限循环保障

满意度闭环是一个**无上限**的迭代过程。只要客户不满意，Consulting Agent 必须回到 Step 1 重新执行完整流程。不存在"最多重试 N 次"的限制。
